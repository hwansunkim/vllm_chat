# Rippletown Methods 리뷰 지침

작성 기준일: 2026년 10월 13일

이 문서는 Rippletown의 논문 Methods를 검토하는 LLM과 공동연구자를 위한 지침이다. 리뷰 대상 초안과 함께 제공하며, 코드를 확인할 수 있다면 관련 구현도 함께 검토한다. 목적은 실제 연구에서 사용하는 핵심 방법을 명료하고 정확하게 설명하는 것이다. 저장소의 모든 기능과 예외를 빠짐없이 문서화하는 것이 아니다.

## 문서의 목적과 독자

검토 대상은 기술 매뉴얼, API 문서, 개발 이력 또는 코드 감사 보고서가 아니라 논문의 방법론 서술이다. 독자는 구현의 모든 분기를 알 필요 없이, 모델이 무엇을 가정하고 에이전트의 행동이 어떻게 세계 상태와 집단 수준 결과로 이어지는지 이해할 수 있어야 한다.

저자는 가독성과 집중도를 위해 구체적인 수치와 모든 세부 옵션을 본문에 열거하지 않았다. 숫자가 없거나 선택 기능이 빠져 있다는 이유만으로 누락을 지적하지 않는다. 핵심 방법의 의미를 이해하는 데 필요한 정의와, 실제 결과의 해석을 바꾸는 가정에 집중한다. 실험 재현에 필요한 설정은 실험 설정 절, 표, 부록 또는 공개 설정 파일에 제시할 수 있다. 모든 재현성 정보를 이 개요 서술에 밀어 넣지 않는다.

## 저자가 확정한 현재 연구 범위

다음 사항은 저자가 직접 설명한 현재 연구 방향이다. 코드의 기본값이나 오래된 분기가 이 설명을 자동으로 대체하지 않는다. 이후 저자가 연구 범위를 변경하면 그에 맞게 갱신한다.

| 항목 | 현재 연구에서의 위치 | 리뷰 시 적용할 기준 |
| --- | --- | --- |
| 공간 | 장소와 구역에 기반한 공간 모델이 핵심 | 공간 없는 실행은 공간 모델 도입 전의 잔존 경로다. 본문에 그 호환 경로를 추가하라고 요구하지 않는다. |
| 시간 | 장면의 경과 시간을 AI가 직접 추론하는 방식이 최종 방향 | 고정 간격, 카테고리 선택 후 무작위 추출, AI 직접 추론이라는 발전 과정 전체를 지원 모드 목록으로 나열하지 않는다. 현재 방법을 직접 추론 중심으로 기술한다. |
| 하루 일과 | 시나리오 이벤트를 통해 일정을 주입 | 에이전트가 모든 일과를 자발적으로 만들어낸다고 서술하지 않는다. 일정 입력과 그에 대한 생성된 행동을 구분한다. |
| 시스템 에이전트 또는 감독 | 현재 연구에서는 사용하지 않는 보조 기능 | 기억과 일과 수행 문제를 보완하려고 도입했으나 현재는 시나리오 이벤트로 일과를 지원한다. 향후 활용 가능성 때문에 코드에 보존되어 있다. 본문의 주요 구성요소에서 제외한다. |
| 언어 교잡 수정 | 저성능 로컬 LLM 사용 중 추가한 임시 보조 옵션 | 현재 핵심 방법으로 다루거나 모든 재시도 동작을 본문에 설명하도록 요구하지 않는다. |
| 개발 및 테스트 기능 | 저장소에 남아 있을 수 있음 | 코드에 존재한다는 사실만으로 연구에 사용됐다고 판단하지 않는다. |

여기서 명시하지 않은 다른 기능까지 임의로 미사용 또는 필수라고 분류하지 않는다. 예를 들어 역할형 에이전트, 동행, 기억 병합의 실험상 사용 여부는 해당 초안, 설정 또는 추가 저자 설명에 근거해 판단한다.

## 코드와 원고를 대조하는 원칙

리뷰의 비교 대상은 원고와 저장소 전체의 기능 목록이 아니라, 원고와 현재 연구에 사용되는 실행 경로다. 저자의 설명은 연구 의도와 범위를 정하고, 코드는 그 범위에서 실제 동작이 서술을 뒷받침하는지 확인하는 근거다.

1. 먼저 원고가 주장하는 핵심 방법과 실제 사용 범위를 파악한다.
2. 관련 코드를 볼 때 핵심 실행 경로, 내부 보조 처리, 사용하지 않는 선택 기능, 이전 버전 호환 경로, 개발용 기능을 구분한다.
3. 코드에 옵션이나 기본값이 있다는 사실을 실제 실험 설정의 증거로 사용하지 않는다.
4. 핵심 경로의 동작이 원고와 실제로 다르면, 그 차이가 독자의 모델 이해나 결과 해석을 어떻게 바꾸는지 설명한다.
5. 미사용 경로의 차이와 사소한 구현 예외는 Methods의 필수 수정 사항으로 제시하지 않는다.
6. 실패 처리나 fallback이 실제 실험에 자주 개입해 결과에 영향을 줄 수 있다면, 조건부로 실험 설정이나 한계 보고의 필요성을 제안한다. 가능성만으로 본문에 예외 목록을 추가하지 않는다.
7. 코드 접근이 없다면 문장 논리와 개념을 검토하되, 구현 확인을 했다고 주장하지 않는다. 과거 코드 검토 결과를 최신 버전에 그대로 적용하지 않는다.

실제 연구 경로에 결과를 바꾸는 구현 오류가 발견되면 문장을 부정확하게 바꿔 숨기지 않는다. 오류 후보와 방법론 설명을 분리하고, 해당 실행 경로에서의 확인 또는 구현 수정이 필요한지 밝힌다. 다만 일반적인 Methods 리뷰를 요청하지 않은 전면 코드 감사로 확대하지 않는다.

## 우선적으로 평가할 사항

### 핵심 방법의 인과관계

독자가 시나리오 입력, 에이전트 지각과 기억, 행동 생성, 엔진의 상태 갱신, 시간 진행, 접촉 또는 다른 분석 대상의 계산 사이의 관계를 따라갈 수 있는지 검토한다. 모든 함수나 처리 분기를 나열하는 대신, 설명이 빠지면 모델의 작동 원리를 다르게 이해하게 되는 부분을 찾는다.

현재 시간 설명은 AI의 경과 시간 추론을 중심으로 해야 한다. 카테고리 분류 뒤 엔진이 시간을 무작위로 추출한다고만 썼다면, 이는 옵션 누락이 아니라 현재 방법 자체를 잘못 설명한 것이므로 우선 수정한다. AI가 시간을 제안하고 엔진이 일정과 상태 제약에 맞게 조정한다는 관계를 명확히 한다.

일과를 시나리오 이벤트로 주입한다는 사실은 핵심 방법이다. 이벤트가 주는 일정이나 자극과, 에이전트가 선택하는 반응을 구분한다. 감독을 제거했다고 해서 외부 일정 입력까지 사라진 완전한 자발적 행동 모델로 묘사하지 않는다.

### 개념과 주장 범위

엔진이 세계를 관리한다는 설명과 모든 과정이 결정론적이라는 주장은 다르다. 결정론, 완전한 물리적 가능성 검증, 정보 무손실, 정확한 재개, 모든 병합의 복구 같은 표현은 그 보장이 실제로 핵심 경로에서 성립할 때만 허용한다.

수정할 때는 예외를 길게 추가하기보다 주장의 범위를 좁혀 핵심을 보존한다. 예를 들어 “engine-managed world dynamics”는 세계 관리 주체를 설명하면서 전체 실행의 결정론을 주장하지 않는다. “structured requests are resolved under spatial and state constraints”는 일반적인 물리 검증을 암시하지 않는다.

프롬프트로 요구하는 행동과 엔진이 강제하는 제약을 구분한다. 자연스러운 서술을 허용하되 프롬프트 지침을 검증된 보장으로 바꾸지 않는다. “LLM calls occur only …”처럼 호출 범위를 전부 열거하는 문장을 쓴 경우에는, 연구에서 사용하는 메모리 압축 등도 포함해야 한다. 그런 열거가 논지에 불필요하면 문장 자체를 삭제할 수 있다.

### 방법론적 가정과 결과 해석

주요 분석의 의미를 바꾸는 가정은 숫자와 무관하게 설명해야 한다. 예를 들어 접촉 계산에서 wave 시작의 접촉 구성을 해당 wave 전체에 적용한다는 가정, 또는 감염 파라미터 재분석에서 원래 행동 궤적을 고정한다는 가정은 관련 분석을 원고가 다룰 때 명시한다.

행동 고정 재분석과 감염 상태 변화에 대한 행동 반응까지 새로 생성하는 실험을 혼동하지 않는다. 연구에서 수행하지 않은 재분석 기능을 코드에 있다는 이유만으로 본문에 추가하지 않는다.

실제 사람과 유사하도록 설계했다는 설명을 현실 행동의 검증 완료로 해석하지 않는다. 생성된 대화가 모델 내부 행동 맥락을 제공한다는 것과 실제 인간 동기를 입증한다는 것도 구분한다.

### 서술의 집중도

본문에는 현재 사용하는 핵심 메커니즘을 남긴다. 감독의 장문 설명, 언어 교잡 재시도, 이전 시간 모드의 발전 과정, API와 저장 필드 설명, 디버깅 사례는 현재 연구의 논지에 필요하지 않으면 삭제 또는 이동을 권한다.

사용하지 않는 기능의 누락을 보완하는 것보다, 현재 사용하지 않는 기능이 주요 방법으로 남아 있는지 먼저 확인한다. 구체적인 상수, 함수명, 정규식, CSV 열 이름을 추가하는 것이 언제나 정확한 논문 서술은 아니다.

## 수치와 구현 상세의 취급

숫자 자체보다 그 값이 수행하는 역할이 핵심이면 개념적으로 설명해도 된다. 예를 들어 “기억이 문맥 예산에 가까워지면 압축한다”, “일정이나 상태 종료를 넘지 않도록 시간 진행을 제한한다”, “관련된 기존 사실을 먼저 검색한 뒤 병합한다”는 설명은 구체적인 임계값이 없어도 방법을 전달할 수 있다.

실험 결과를 비교하거나 재현하는 데 특정 값이 중요한 경우에는 실험 설정 또는 보충자료에서 보고할 것을 제안한다. 이때 어떤 결과 해석에 필요한지 함께 설명한다. 수치 표가 없다는 이유만으로 개념 중심의 Methods 초안을 부적합하다고 판정하지 않는다.

알고리즘의 구체화도 같은 기준을 적용한다. 사실 검색이 논문의 주요 기여라면 검색 기준을 더 설명할 수 있다. 기억 유지가 전체 시뮬레이터를 지원하는 구성요소라면, 검색과 병합의 개념만으로 충분할 수 있다. 코드 수준 설명의 필요성을 기여도와 연결해 판단한다.

## 권장 리뷰 출력

리뷰는 한국어로 작성하고 필요한 대체 문장은 원고와 같은 영어로 제시한다. 다음 순서를 따른다.

1. 전체 평가: 핵심 방법의 전달력과 논문 서술로서의 적합성을 짧게 평가한다.
2. 필수 수정: 현재 사용되는 방법을 잘못 설명하거나 결과 해석을 바꾸는 주장만 우선 제시한다. 각 항목은 원문, 문제의 의미, 최소 수정안으로 구성한다.
3. 삭제 또는 축소: 미사용 보조 기능과 개발 설명 중 논지에 불필요한 내용을 제시한다.
4. 선택적 개선: 흐름과 용어를 개선할 제안을 필수 수정과 구분한다. 숫자나 상세 알고리즘 추가는 필요성이 있을 때만 제안한다.
5. 저자 확인 사항: 연구의 의미를 바꿀 정도로 필요한 질문만 남긴다. 위에서 이미 확정된 사용 범위를 다시 질문하지 않는다.

코드 근거는 리뷰의 증거로 짧게 제공할 수 있다. 대체 원고 문장에는 코드 경로와 내부 구현명을 불필요하게 넣지 않는다. 발견한 차이를 모두 나열하지 말고 중요도가 높은 소수의 수정에 집중한다. 올바른 내용은 올바르다고 평가하며, 단순화를 정확성 문제로 과장하지 않는다.

## 이번 초안에 적용할 초기 판단

- 시간 절은 카테고리 기반 무작위 추출 대신 AI의 직접 경과 시간 추론을 중심으로 수정한다.
- Director agent 절과 wave 처리 중 감독 호출은 현재 연구의 주요 방법에서 제외한다. 향후 기능 소개가 목적이 아니라면 옮길 필요 없이 생략해도 된다.
- 언어 교잡 수정은 현재 핵심 방법에서 제외한다.
- 시나리오 이벤트를 통한 일과 입력과 그 입력에 대한 에이전트의 행동 선택 관계는 유지하거나 명확히 한다.
- 공간 모델을 중심으로 서술하고, 공간 없는 레거시 실행은 언급하지 않는다.
- 결정론, 실패 메시지 무손실 재전달, exact resume, 병합 undo를 단정하는 문장은 핵심 설명을 보존하면서 실제 보장 범위로 완화한다.
- 기억 처리와 접촉 계산의 최근 변경은 현재 구현에 맞게 인정한다. 과거 버전의 지적을 반복하지 않는다.
- 원고가 접촉 기록의 재분석을 장점으로 제시한다면 행동 고정 가정도 함께 설명한다.
- 수치, 모든 모드와 예외, 개발 및 테스트 기능의 목록을 본문에 추가하라는 요구는 기본적으로 하지 않는다.

## 다른 리뷰 LLM에 전달할 요청문

이 지침과 첨부한 Rippletown Methods 초안을 함께 읽고 리뷰하라. 이 원고는 기술 매뉴얼이 아니라 현재 연구에 사용하는 핵심 방법을 설명하는 논문 초안이다. 공간 모델, AI의 직접 시간 추론, 시나리오 이벤트 기반 일과 입력을 중심으로 평가하라. 감독과 언어 교잡 수정은 현재 연구에서 사용하지 않는 보조 기능이며, 이전 시간 모드와 공간 없는 호환 경로를 추가하도록 요구하지 마라. 수치나 모든 옵션의 생략 자체를 결함으로 보지 마라. 대신 핵심 인과관계, 연구 가정, 과도한 보장, 프롬프트 지침과 엔진 제약의 구분을 확인하라. 코드가 제공되면 현재 연구 경로에 해당하는지 먼저 판별하라. 필수 수정, 삭제 또는 축소, 선택적 개선을 구분하고 원래 초안의 집중도를 유지하는 최소한의 영어 대체 문장을 제안하라. 명시적으로 요청받지 않았다면 원고나 코드를 직접 수정하지 마라.
