# to_serve 시나리오 리뷰에 대한 비판적 검토

- 작성일: 2026-10-16
- 검토 대상: [case1_v12-scenario-review-2026-10-16.md](../to_serve/case1_v12-scenario-review-2026-10-16.md), 158행
- 검토 범위: 주장 정확성, 실행 근거, 개선안의 구현 가능성과 부작용, 연구 결과 해석, 빠진 주요 문제
- 검토 방식: 원본 JSON 2개, 참고 실행 Markdown, 위치 이력 CSV, 저장된 실행 설정·이벤트, 현재 엔진 코드와 대조
- 원문과 시나리오·엔진은 수정하지 않았다. 별도의 전체 LLM 시뮬레이션은 실행하지 않았다.

## 판정

**문제 탐지에는 유용하지만, 권장 수정안을 그대로 적용하기에는 중요한 보완이 필요하다.** 이벤트 시각 불일치, 검사 절차의 공백, 공간 집계 문제, 고정 증상 문구에 관한 지적은 대체로 타당하다. 접촉 시간과 감염 확률 수치도 원본 CSV로 재현됐다.

반면 다음 권고는 그대로 적용하면 새로운 문제를 만들거나 원래 문제를 해결하지 못한다.

1. 의사 에이전트 추가만으로 엔진 감염 상태에 근거한 검사 결과가 생성되지는 않는다.
2. `동네.is_exterior=true`는 장소를 세분화하는 설정이 아니라 그 장소에서의 대화·접촉을 차단하는 설정이다.
3. 공통 수면 시간을 7–10시간으로 바꾸면 새벽 재수면 때도 7–10시간을 다시 부여하는 문제가 남는다.
4. β 재계산은 원래 행동을 고정한 민감도 분석이며, 새 감염에 반응하는 행동 변화까지 재현하지 않는다.

또한 참고 실행은 검토 대상 JSON과 시작 인물이 다르다. 일부 단일 실행 관찰을 “매일” 또는 일반적 시나리오 결함으로 확대했고, 집을 경유하는 외부 이동 경로와 추가 확진자의 일정 처리라는 핵심 문제를 빠뜨렸다.

이 문서에서 **P1**은 권고 적용 또는 연구 해석 전에 해결해야 할 문제, **P2**는 근거·설계·검증을 보완해야 할 문제, **P3**는 표현·가독성 문제를 뜻한다.

## 1. P1 — ‘의사 추가’는 검사 결과의 진실성을 보장하지 않는다

**원문 위치:** 44–56행, 문제 1.

검사 결과를 확정하는 절차가 없다는 지적은 맞다. 그러나 “2차 감염자는 확진될 수 없고 격리에 들어갈 수도 없다”는 단정과 “역할형 의사를 두면 해결된다”는 처방은 구분해야 한다.

현재 엔진은 에이전트에게 자신의 증상 서사를 전달하지만 감염 상태의 원시값은 보여 주지 않는다. 역할형 에이전트는 이동·자동 호출 등에 별도 규칙을 적용받을 뿐, 환자의 감염 상태를 조회하는 검사 권한을 얻지 않는다. 근거: [prompt_contract.py](../ABM/prompt_contract.py)의 `build_infection_contract`와 역할형 계약, [core.py](../ABM/simulation/core.py)의 `_role_type_agents`, [schemas.py](../backend/api/simulation/schemas.py)의 `AgentConfig.role_type`.

따라서 의사만 추가하면 증상과 대화를 바탕으로 **양성·음성 결과를 LLM이 만들어 내는 상황**이 생길 수 있다. 반대로 의사가 없어도 환자가 대사에서 자가검사 양성을 주장하거나 자발적으로 격리하는 것은 생성상 가능하다. 정확한 결함은 “확진·격리가 절대 불가능”이 아니라 **검사 결과와 엔진 상태의 일관성을 보장할 경로가 없다**는 것이다.

원문 52행의 “경증이면 병원에 가지 말라”는 해석에도 범위 문제가 있다. JSON의 해당 문장은 **이미 확진된 경증 환자**의 경과 관찰에 관한 것이다. 검사 전 의심자의 병원 검사까지 명시적으로 금지한 것으로 읽어서는 안 된다.

**수정 권고**

- 검사 요청, 검체 채취 시점, 결과 통보 시점, 결과 판정 규칙을 먼저 정의한다.
- 결과는 엔진의 감염 상태와 명시적인 검사 가정에 따라 결정하고, 의사는 그 결과를 전달하거나 진료하는 역할로 둔다. 이상적인 검사로 단순화할지, 상태·시점별 검출 가능성을 둘지도 실험 가정으로 기록한다.
- 검사 양성 사실과 격리 시작·종료는 기억 속 대사에만 맡기지 않고 추적 가능한 상태 또는 이벤트로 남긴다.
- 의사를 추가한다면 감염 계산 참여 여부도 결정해야 한다. 현재 접촉 그룹 계산은 `role_type`을 이유로 자동 제외하지 않으므로, 활성 상태인 의사가 추가 감염자나 전파원이 되어 원래의 4인 가구 실험 범위를 바꿀 수 있다.

**완료 판단:** 검사 결과가 엔진 상태·검사 규칙과 일치하고, 결과 통보 후 대상자에게만 격리 상태가 적용되는 사례를 확인해야 한다. 의사가 “양성입니다”라고 말하는 것만으로는 충분하지 않다.

## 2. P1 — `is_exterior=true`를 우선 처방하는 것은 실험 가정을 바꾼다

**원문 위치:** 99–105행, 문제 7; 155행의 최우선 권고.

마트·카페 등을 `동네` 하나로 묶으면 서로 다른 장소의 사람을 동석자로 처리할 수 있다는 지적은 맞다. 다만 `is_exterior=false` 자체가 잘못인 것은 아니다. 집 밖의 실제 만남도 관찰하려면 외부 장소가 상호작용 가능한 일반 노드여야 할 수 있다.

현재 코드에서 `is_exterior=true`의 의미는 다음과 같다.

- 같은 노드에 있어도 일반적인 대화 도달성이 차단된다. [targets.py](../ABM/simulation/targets.py), `_same_room`, 204행 이후.
- 해당 장소의 사람은 일반 접촉 그룹에서 제외된다. [infection.py](../ABM/simulation/infection.py), `_compute_contact_groups`, 366행 이후.

즉 서로 다른 가게에 있는 사람의 가짜 접촉뿐 아니라, **실제로 같은 가게에서 만난 가족의 접촉도 제거한다.** ‘외부 공간’이라는 명칭을 현실의 실외·집 밖이라는 뜻과 혼동하면 안 된다.

이전 v3에서 `동네.is_exterior=true`였다는 사실은 `memory.db`의 `simulation_scenarios`에서 확인했다. 평면도 SVG에 exterior라고 표시된 것도 맞다. 그러나 과거 설정과 그림은 현재 연구 목적에 맞는 정답을 입증하지 않는다.

**수정 권고**

- 집 밖을 관찰하지 않는 실험이라면 `is_exterior=true`를 의도적 경계 조건으로 명시한다.
- 집 밖의 만남도 분석한다면 마트·카페 등을 별도 노드로 나누고, 같은 장소에 있을 때만 접촉하도록 한다.
- 그림은 확정된 실험 설정에 맞춘다. 그림과 다르다는 이유만으로 모델을 과거 설정으로 되돌리지 않는다.

## 3. P1 — 외부 이동이 반드시 집을 거치는 지도 문제를 누락했다

**원문 위치:** 위치 그래프를 모두 검토했다는 13행 및 문제 7.

두 JSON의 외부 장소는 모두 `우리집`만 연결 대상으로 가진다. 현재 엔진의 실제 경로 탐색 함수를 두 설정에 적용하면 다음 경로가 나온다.

| 의도한 이동 | 계산된 경로 |
|---|---|
| 학교에서 집에 들르지 않고 학원으로 | `고등학교 → 거실 → 누나학원` |
| 퇴근 후 사람을 만나러 외출 | `회사 → 거실 → 동네` |

이는 인물 프롬프트에 명시된 행동과 직접 충돌한다. 외출·귀가 횟수, 가족과의 접촉, 이동 시간을 바꿀 수 있으므로 카테고리 ID나 나이 표기보다 우선순위가 높다. 근거: [location.py](../ABM/simulation/location.py)의 `_expand_zone_edges`, `_find_path`, `_find_path_zoned`.

**수정 권고:** 필요한 외부 장소 간 연결을 정의하고 이동 시간까지 함께 검토한다. 현재 외부 노드들은 `zone=""`이므로 간선만 연결하면 두 외부 노드 사이에서 구역 경계 이동 시간 10–20분이 적용되지 않는다. 경로 수정과 시간 모델 수정은 별개로 확인해야 한다. 근거: [runner.py](../ABM/simulation/runner.py)의 `_move_one_hop`에서 `crossing_zone` 판정.

## 4. P1 — β 계산은 맞지만, 권고된 재분석과 보정의 해석 범위가 빠졌다

**원문 위치:** 86–91행, 문제 5.

위치 CSV의 wave 시작 위치·감염 상태와 해당 wave의 경과 시간을 이용해 다시 계산했다. 외부 공간과 이동 중 상태도 확인했으며, 이 실행에서 짱구와 다른 가족의 유효 접촉 시간은 아래와 같다.

| 짱구와의 접촉 대상 | 접촉 시간 | 시간 환산 | β=0.04/일의 쌍별 감염 확률 |
|---|---:|---:|---:|
| 봉미선 | 1,513분 | 25.2167시간 | 4.1157% |
| 신영식 | 286분 | 4.7667시간 | 0.7913% |
| 신짱아 | 61분 | 1.0167시간 | 0.1693% |

계산식은 `p_i = 1 - exp(-0.04 × 접촉분_i / 1440)`이다. 기록된 동선을 고정하고 짱구가 감염원인 조건에서 가족 중 한 명 이상이 감염될 확률은 `1 - exp(-0.04 × 1860 / 1440) = 5.0355%`다. 원문의 반올림 수치와 일치한다. 이 값은 실제 코로나19 위험의 측정치가 아니라 모델 내부 계산값이다.

그러나 개선안에는 세 가지 한계가 추가되어야 한다.

1. **β 재계산은 행동을 고정한다.** 새 감염이 발생해도 그 사람이 새로 검사받거나 격리하거나 접촉을 줄이는 행동은 생성되지 않는다. 도구 자체가 이 한계를 명시한다. [rebeta.py](../ABM/tools/rebeta.py), 모듈 설명의 ‘고정 행동 가정’.
2. **특정 가구의 한 번의 동선에 문헌 감염률을 맞추는 것만으로 보정이 끝나지 않는다.** 비교 문헌의 관찰 기간, 변이·면역·가구 구성·접촉·격리 조건을 정하고, 여러 행동 실행에 걸친 분포로 검토해야 한다. 이 실행의 무감염 결과 하나는 β의 경험적 타당성을 확인하는 근거가 아니다.
3. **‘보호 행동은 전파 확률에 반영하지 않았다’는 표현은 너무 넓다.** 마스크·환기·손 씻기의 직접 효과는 별도 계수로 반영되지 않지만, 방을 나눠 쓰거나 동석 시간을 줄이는 행동은 접촉 시간과 그룹을 통해 반영된다.

권장 대체 문장:

> 마스크·환기·손 위생의 직접적인 위험 감소 계수는 모델링하지 않았다. 격리 및 공간·시간 분리를 통한 접촉 변화는 위치 이력에 반영된다. β 재계산은 해당 위치 이력을 고정한 조건부 민감도 분석이며, 추가 감염에 따른 행동 반응은 포함하지 않는다.

## 5. P2 — 참고 실행이 검토 대상 JSON과 완전히 같지 않다

**원문 위치:** 7–17행, 검토 대상 및 실행 대조 설명.

저장된 실행 설정과 O JSON을 비교한 결과, 공통 키 중 값이 실제로 다른 것은 `start_agent`였다. 정수/실수 직렬화 차이는 제외했다.

| 항목 | 검토 대상 O JSON | 참고 실행의 저장 설정 |
|---|---|---|
| `start_agent` | 봉미선 | 신영식 |
| `max_waves` | 4000 | 4000 |
| `target_duration_minutes` | 10080 | 10080 |

실행 로그 wave 0도 실제로 신영식의 행동부터 시작한다. 따라서 참고 실행은 대부분의 설정을 공유하는 **변형 실행**이며, 정확히 같은 JSON을 실행한 결과라고 취급하면 안 된다. 시작 인물 차이의 효과가 얼마나 큰지는 별도 비교 없이 알 수 없지만, 초기 상호작용과 후속 행동에 영향을 줄 수 있다.

추가로 집계 기준을 정리해야 한다.

- Markdown 헤더는 `Wave 1000 · 총 턴 1979`라고 표시한다.
- 실제 wave 번호는 0–1000으로 **1,001개**이고, 위치 CSV는 4명 × 1,001개 = **4,004행**이다.
- `simulation_log`의 실제 행 수는 **1,979개**다.
- `simulation_runs` 메타데이터에는 `total_waves=1001`, `total_turns=1980`이 저장되어 있어 턴 수가 로그와 다르다. 원인의 별도 조사는 이 리뷰 범위 밖이다.
- CSV 마지막 종료 경과분은 **10,085분**, 즉 7일 5분이다. 목표 10,080분과 구분해야 한다.
- X의 이벤트는 **14개**, O의 이벤트는 **15개**다. 13행의 ‘이벤트 15개’는 O에 한정해 표기하는 편이 정확하다.

**수정 권고:** 실행 ID, 실제 실행 설정, 엔진 버전, wave 인덱스와 개수의 구분, 실제 관찰 기간을 명시한다. 검토 대상 JSON과 참고 실행의 차이를 각주로 남긴다.

## 6. P2 — 수면 범위 변경은 ‘남은 잠을 새 수면으로 재추첨’하는 문제를 해결하지 않는다

**원문 위치:** 119–125행, 문제 9.

공통 5–9시간 범위와 짱구의 ‘8시간 넘게 잔다’는 설정이 불일치한다는 지적은 맞다. 그러나 7–10시간으로 바꾸는 것을 우선 해결책으로 제시하면, 딸의 약 6시간 수면 설정과 충돌하고 새벽 재수면 때 긴 시간이 다시 부여된다.

실행에서 확인한 사례:

| wave | 시각 | 짱구의 수면 진입 및 새 타이머 |
|---:|---|---|
| 3 | 월요일 06:05 | ‘조금만 더 잔다’ → 329분, 11:34까지 |
| 138 | 화요일 05:55 | 재수면 → 357분, 11:52까지 |
| 277 | 수요일 04:36 | 재수면 → 303분, 09:39까지 |
| 422 | 목요일 02:52 | 재수면 → 374분, 09:06까지 |
| 687 | 토요일 04:18 | 재수면 → 347분, 10:05까지 |
| 857 | 일요일 06:33 | 재수면 → 325분, 11:58까지 |

현재 초기 `_agent_status`는 빈 상태다. 이미 자고 있다는 배경 설명만으로 남은 수면 시간이 저장되지 않는다. 또 수면 상태가 만료된 뒤 다시 수면에 진입하면 공통 범위에서 전체 시간을 새로 뽑는다. 같은 상태가 아직 유효한 동안의 재선언은 타이머를 늘리지 않는다는 점과 구분해야 한다. 근거: [core.py](../ABM/simulation/core.py), 307행; [status.py](../ABM/simulation/status.py), `_enter_state`, 230행 이후.

‘매일 밤 두 번’이라는 표현도 수정해야 한다. 완료된 월→화부터 토→일까지 6개 밤 중 5개에서 새벽 재수면을 확인했다. **금요일 06:21 이후에는 새 수면 진입이 없었다.** 일→월 수면의 예정 종료는 관찰 종료 이후라 완결된 밤으로 세면 안 된다.

**수정 권고:** 초기 수면의 남은 시간, 짧은 재수면, 새로운 야간 수면을 구분하고, 필요하면 인물별 수면 목표를 둔다. 공통 범위를 늘리는 것만으로 해결됐다고 판단하지 않는다.

## 7. P2 — 단일 O 실행의 생활 패턴을 X·O 공통 결함으로 일반화했다

**원문 위치:** 127–131행, 문제 10; 35행 및 123행의 반복 빈도 표현.

엄마가 한 번도 외출하지 않았다는 관찰과 아빠가 주말에 두 번 동네에 나갔다는 관찰은 확인된다. 그러나 이것만으로 X에서도 일상 다양성이 부족하다거나, 엄마의 외출 이벤트가 없어서 그렇다고 결론 내릴 수 없다. O에는 아픈 아이를 돌보는 상황이 추가되어 있다.

‘매일 12시 20분께 180분짜리 idle 점프’도 실제 기록과 다르다. `sim_events.time_jump`에서 `mode=idle`, `minutes=180`인 사건은 다음 **4개**다.

| wave | 시작 | 종료 |
|---:|---|---|
| 51 | 월요일 12:24 | 월요일 15:24 |
| 191 | 화요일 12:18 | 화요일 15:18 |
| 327 | 수요일 12:23 | 수요일 15:23 |
| 605 | 금요일 12:20 | 금요일 15:20 |

이는 목요일과 주말까지 포함하는 ‘매일’이 아니다. 시간 압축이 발생했다는 사실도 활동이 전혀 없었다거나 시나리오가 실패했다는 뜻은 아니다.

**수정 권고:** ‘이 O 실행에서 관찰됨’으로 한정한다. 자율성이 연구 대상이라면, 관찰한 패턴이 마음에 들지 않는다는 이유만으로 장보기 이벤트를 추가하면 행동을 입력으로 강제하는 개입이 된다. 같은 생활 설정에서 X·O를 반복 실행해 외출 횟수·가족 접촉·활동 다양성의 분포를 비교한 뒤 결정해야 한다.

## 8. P2 — 격리 종료·회복·일정 재개를 분리하고 추가 확진자까지 다뤄야 한다

**원문 위치:** 58–84행, 문제 2–4; 156행의 ‘문구·설정 수정만으로 해결’ 권고.

격리 종료일이 모호하다는 지적은 타당하다. 다만 다음 세 가지는 서로 다른 시계다.

1. 검사 양성 시점을 기준으로 한 시나리오상 격리 기간.
2. 엔진의 I 단계 8일과 회복 전이 시점.
3. 등교·출근·학원 일정을 다시 수행할 시점.

I 후반 문구를 ‘기침만 남음’으로 바꾸면 주관적 회복감은 달라질 수 있지만 엔진의 전염 기간이나 격리 종료 시점이 자동 변경되는 것은 아니다. ‘주말까지 격리한 원인이 고정 증상 문구’라는 원문 표현은 가능한 설명이며, 원인을 분리한 실험으로 확인된 사실은 아니다.

이번 설정은 월요일 05:50에 시작해 목표상 다음 월요일 05:50에 끝난다. 짱구의 등교 재개 알림은 그날 08:25이고, I 단계 8일을 모두 거친 회복은 9일차 화요일 05:50 이후 판정 대상이다. **등교 복귀와 회복을 평가하려는 목적이라면 관찰 기간 자체가 부족하다.** 5일 격리 후 다음 월요일에 학교에 가는 것은 주말 때문에 가능한 일정이므로, `from_day: 8` 자체를 5일 격리와의 모순으로 취급할 필요는 없다.

더 중요한 누락은 **추가 확진자 일정**이다. 짱구 이벤트만 8일차로 미뤄졌고, 아빠·누나가 나중에 확진되어도 출근·등교 알림은 계속 전달된다. ‘격리자는 시간표에서 빠진다’는 배경 문장만으로는 상충하는 알림이 없어진 것이 아니다.

**수정 권고:** 격리 우선순위, 확진자별 일정 예외, 확진 시각별 해제 계산을 명시한다. 고정 토요일 해제 이벤트를 사용한다면 최초 환자인 짱구에게만 적용하고, 늦게 확진된 가족까지 일괄 해제하지 않도록 대상·일차를 제한해야 한다. 알림은 위치를 강제로 고정하지 않으므로 실제 외출 여부도 따로 확인해야 한다.

## 9. P2 — 임상 용어와 현실 방역 지침의 검증이 빠졌다

**원문 위치:** 70–84행 및 81행의 잠복기 설명.

이 엔진의 E는 ‘감염됐지만 전염력이 없는 구간’으로 구현되어 있다. 이를 임상적인 잠복기 전체와 동일시하면 안 된다. 임상 잠복기는 감염에서 증상 발현까지의 기간이며, 코로나19는 증상 전에도 전파될 수 있다. 이 구분은 WHO의 전파 설명에서 확인할 수 있다. [WHO: 코로나19 전파 방식](https://www.who.int/news-room/questions-and-answers/item/coronavirus-disease-covid-19-how-is-it-transmitted), [WHO: 잠복기 정의와 증상 전 전파](https://www.who.int/docs/default-source/coronaviruse/situation-reports/20200402-sitrep-73-covid-19.pdf)

이 설정에서 검토할 문제는 구체적으로 다음과 같다.

- E부터 가벼운 증상이 주어져 검사 행동을 유도할 수 있다.
- P는 0일이라 증상 전 전염 단계를 표현하지 않는다.
- E 문구를 ‘더 약하게’ 바꾸는 것만으로 증상 기반 검사 규칙과의 연결이 사라지지는 않는다.

따라서 E의 의미, 증상 발현 시점, 전염 시작 시점을 먼저 정의하고 문구와 기간을 맞추는 것이 필요하다. SEIR 단순화 자체를 무조건 오류라고 판정할 필요는 없다.

또한 원문은 JSON이 ‘정부·보건당국 지침’으로 제시한 5일 격리를 검증하지 않았다. 질병관리청 2026년 관리지침은 주요 증상이 호전된 뒤 24시간이 지날 때까지 격리를 권고한다. 5일을 연구용 고정 조건으로 쓰려면 **현실 지침이 아니라 시나리오의 가정**으로 명시해야 한다. 파일 내보내기 날짜가 곧 이야기의 시대 배경이라는 뜻도 아니므로, 과거 시기의 정책을 재현하는 경우에는 적용 시기를 적는 것이 맞다. [질병관리청 2026년 관리지침](https://kdca.go.kr/bbs/kdca/55/309272/download.do)

## 10. P2 — 특정 엔진 수정과 전체 생활 패턴 해결을 구분해야 한다

**원문 위치:** 146–156행, 이미 해결된 문제 및 권장 순서.

커밋 `6ca0b473a9645f23ca47fce6d12f41d70e6d58fb`은 실제 존재하며, 혼자 깨어 다중 hop 이동 중인 사람에게 반복 idle 점프가 붙는 경우를 수정한다. 관련 회귀 테스트도 직접 실행해 통과를 확인했다.

```text
Ran 1 test — OK
```

따라서 해당 원인에 대한 코드 수정 주장은 근거가 있다. 다만 이를 근거로 모든 늦은 취침을 엔진 문제로만 분류하거나, 현재 서비스에서 문제가 해결됐다고 단정해서는 안 된다. 회귀 테스트는 특정 경로를 검증하며, 시나리오 전체 재실행이나 현재 서버의 코드 버전을 확인한 것은 아니다.

**수정 권고:** ‘해당 경로의 코드 수정 및 회귀 테스트 확인, 수정된 엔진으로 전체 시나리오 재검증 필요’로 범위를 한정한다. ‘문구·설정 수정만으로 주말 격리와 새벽 기상을 해결한다’는 156행도 결과 보장 대신 검증해야 할 가설로 바꾸는 것이 맞다.

## 11. P3 — 나이와 내부 카테고리 ID는 오류로 과장하지 않는 편이 좋다

**원문 위치:** 133–144행, 문제 11–12.

- `night_sleep`에 낮 활동 설명이 연결된 점은 가독성 문제다. 원문도 AI 직접 추론 모드에서는 전체 범위만 사용한다고 구분한 점이 적절하다. 현재 엔진은 시간 카테고리 ID를 불투명한 키로 취급하므로, ID만 바꾸면 시간 동작이 교정되는 것으로 설명해서는 안 된다.
- ‘13세·초등학교 6학년은 한국식 나이’라고 단정할 정보는 없다. 통상적인 학년 나이를 추정하는 것과 해당 인물의 나이 기준을 확인하는 것은 다르다. 출생연도·기준일·만 나이 여부를 설정에 명시한 뒤 번역해야 하며, 자동으로 11–12세로 바꾸는 것은 피해야 한다.

### 접촉 시간 재계산 기준

CSV는 발화자만 기록한 구형식이 아니라, 매 wave 활성 4명의 위치·상태·이동 여부를 기록한 명단 형식이다. 총 4,004행, 1,001 wave를 확인했다. 각 wave에 대해 시작 시점의 짱구와 다른 가족의 위치·감염 상태를 확인하고, 해당 wave의 `elapsed_minutes_end - elapsed_minutes_start`를 유효 접촉에 합산했다. 실제 접촉 합계는 1,860분이다. 일반화할 때는 이동 중 동행 그룹도 접촉이 될 수 있다는 엔진 규칙을 보존해야 한다.

엄마·아빠·누나는 모든 wave 시작에서 S, 짱구는 I였다. 감염 이벤트는 최초 환자 지정 1건뿐이고, 추가 노출은 없었다. 따라서 ‘참고 실행에서 2차 감염이 없었다’는 원문 주장은 확인됐다.
